## Summary

The eight highest-risk items called out by the orchestrator are genuinely fixed and match the design:

1. **Indexing is default-deny** — confirmed. `server/src/robots.ts` and `src/lib/indexing.ts` both use an explicit `INDEXABLE_PATHS = Set(['/', '/entrar'])` with exact-match-after-single-trailing-slash-strip, no case folding, no prefix matching. `/g/:groupId`, `/join/:token`, `/assets/*`, and every unknown path fall through to `noindex, nofollow` by construction (absence from the allowlist, not an exclusion list). `public/robots.txt` and `deploy/Caddyfile`'s `@indexable` matcher both mirror the same two paths and default to `noindex, nofollow` otherwise, with the Caddy header serving as the documented single-point kill switch. `index.html`'s blanket meta is removed; `SeoRobots.tsx` is a client-side mirror only, explicitly documented (and true) as unable to override a stricter server header. No route can become indexable by omission.
2. **Quorum cap** — confirmed. `required_participants(member_count, pct) = greatest(1, least(member_count, ceil(member_count*pct/100)))` in `db/migrations/600_quorum_and_open_close.sql`, evaluated live via a `left join lateral` member count in `PREDICTION_SELECT` (`server/src/prediction-select.ts`) and inside `finalize_predictions`/`refresh_prediction_counts`/`request_close` via `group_member_count()`. A 2-member group qualifies (`integration/prediction-qualification.test.ts`), and the requirement recomputes on every read rather than being frozen at creation (no stored "required" column exists — it's always derived).
3. **`create_prediction` overload** — confirmed live against the DB: exactly 1 row in `pg_proc` for `proname='create_prediction'`. `610_functions.sql` opens with `drop function if exists public.create_prediction(<exact old 13-arg list>)` before `create or replace` with the new 14-arg signature.
4. **`required_participants` grant** — confirmed live: `authenticated` has `EXECUTE` on `required_participants`, `required_close_requests`, `request_close`, `withdraw_close_request`. `620_rls_and_grants.sql` revokes from `public, anon, authenticated` before granting to `authenticated` for every new/re-signed function, and `group_member_count` is revoked from all three and never re-granted (confirmed live — no grantee rows at all).
5. **`score_prediction` earliness fix** — confirmed both by code and by a live-passing integration test (`prediction-closing.test.ts`, "score_prediction no le da a todo el mundo la anticipación máxima..."). `v_close := coalesce(closes_at, closed_at, resolved_at, now())` replaces the NULL-blind `greatest()`. `closed_at` is populated on the three paths this change added/touched: `finalize_predictions` step 3 (date close), step 4 (close-request quorum via cron), and `request_close`'s in-transaction close. See Finding 4 below for one **pre-existing, untouched** path that does not set it.
6. **Two-step voting** — confirmed genuine on both surfaces. `VoteOption.onSelect` only calls `setStaged(option.id)`; the actual `castVote.mutate(...)` call lives only in each consumer's Confirm button handler (`PredictionDetail.tsx:286-298`, `PredictionCard.tsx:78-103`). The staged state resets via the `voteKey`-diff-during-render pattern (own vote lands, server rejects and the optimistic snapshot rolls back, or status changes) in both files. `useCastVote` (`src/data/predictions.ts:130-210`) is untouched — optimistic update and rollback are preserved exactly, only the call site moved.
7. **`votes_visibility='visible'` renders names on an OPEN prediction** — confirmed real fix. `PredictionDetail.tsx:93` gates `showVoterNames` on `canSeeVotes(data, status)`, not `revealed` alone, and `canSeeVotes()` (`src/lib/prediction.ts:135-142`) mirrors `public.can_see_votes()` (`300_rls.sql:75-93`) exactly: `anonymous` → false, `visible` → true unconditionally, `on_close` → only if revealed. `prediction_votes_select_own_or_visible` RLS already implements the server side of this, so the read-path RLS and the client gate agree.
8. **NULL `closes_at` blast radius** — confirmed NULL-safe end to end: `effectiveStatus`, `isOpenForVoting`, `feedRank`, `sortFeed` (`closesAtMs()` helper → `Infinity`), `PredictionDetail`, `PredictionCard`, `History.tsx` (`resolved_at ?? closed_at ?? closes_at ?? created_at`), and SQL-side `finalize_predictions` step 3, `add_prediction_option`, `cast_vote` all use explicit `is not null and ... <=` comparisons instead of relying on three-valued-logic. `Countdown.tsx` deliberately stays non-nullable per design, gated at both call sites.

## Findings

### CRITICAL

**1. `ParticipationThreshold`'s displayed "X de Y" does not show the live member count — it re-hides the denominator, just with a different number than before.**

- Spec violated: `specs/prediction-qualification/spec.md` → "Requirement: Displayed progress uses the live denominator" — *"The UI MUST show the current live member count as the denominator and the computed requirement as a separately labeled number... GIVEN a 2-member group where both members voted... THEN it shows '2 de 2', not a stale '2 de 3'."*
- Also an explicit, unchecked line in `proposal.md`'s own Success Criteria: *"The visible denominator equals the live group member count, and the requirement is shown and explained separately."*
- File: `src/components/prediction/ParticipationThreshold.tsx:88-103` — the denominator rendered is `requiredParticipants`, not `memberCount`. `memberCount` is used ONLY to cap the face row (`Math.min(requiredParticipants, memberCount)` at line 54); it is never displayed as text anywhere in this component.
- Proof this is not accidentally correct: `src/components/prediction/VoteOption.test.tsx:180-225` renders `requiredParticipants={3} memberCount={5}` and asserts `screen.getByText('2 de 3 personas')` — i.e. the test itself locks in "de 3" (the requirement), not "de 5" (the live member count). The one spec scenario that *is* satisfied ("2-member group → '2 de 2'") only passes because in that specific case `requiredParticipants` happens to equal `memberCount` (both capped to 2) — it does not generalize.
- Impact: this component is what actually renders on `PredictionCard` and `PredictionDetail` while a prediction is `proposed` — the real, everyday "en prueba" UI the owner complained about ("the 'votaron 2 de 3' denominator is a hidden constant, not a real quorum"). In any group where the requirement is below the full member count (the normal case for a <100% quorum, i.e. almost every prediction), the member does not see how large their group actually is — only how many are needed, still presented with the exact same "N de M" grammar as the bug being fixed. `CreatePredictionSheet.tsx:465-470`'s separate "Con {memberCount} personas en el grupo, necesita {required}" sentence is correct, but it only exists on the *creation* form, before any prediction row exists — it does not appear on the card/detail screens where members actually watch qualification progress.
- Not caught by the four green gate commands because the (spec-violating) behavior has its own passing unit test.

### WARNING

**2. DB has no server-side enforcement of "evolutiva interval fits within the closing window" — only the client Zod check exists.**

- Spec violated: `specs/prediction-closing/spec.md` → "Requirement: Evolutiva interval is validated against the closing window" — *"both the client (Zod) and the DB MUST reject an interval that does not fit"*, with its own scenario *"DB rejects the same case if client validation is bypassed."*
- `design.md` also states this explicitly: *"cross-validates the evolutiva interval against the window (Zod + DB)"*.
- Verified: `src/lib/validation.ts:129-139` implements the client-side check correctly (superRefine comparing `intervalDays * DAY_MS` against the window). But `db/migrations/610_functions.sql`'s `create_prediction` body (lines 216-322) has no equivalent check — `p_vote_interval` is only bounded by the pre-existing, unrelated `100_schema.sql:176` constraint (`vote_interval between 1 hour and 90 days`), which has nothing to do with the closing window. Grepped all of `db/migrations/*.sql` for `vote_interval` — no window-vs-interval check exists anywhere.
- Confirmed untested: no integration test calls `create_prediction` with an oversized `p_vote_interval` and asserts rejection (`integration/flow.test.ts:370` is the only `p_vote_interval` usage in the whole `integration/` tree, and it's a normal, in-window case).
- Impact: a client that bypasses the form (direct RPC call, a future client, or a bug) can create an evolutiva prediction whose interval never fits before the close date, producing zero valid rounds server-side with no defense-in-depth — the exact scenario the spec's "DB rejects... if client validation is bypassed" was written to prevent.

**3. `HelpTip` uses `aria-controls`, not the `aria-describedby` the spec text literally requires — an unreconciled spec/design conflict.**

- Spec: `specs/prediction-settings-help/spec.md` → "Requirement: Correct ARIA state and association" — *"The trigger MUST carry `aria-expanded`... and MUST carry `aria-describedby` pointing to the id of the rendered help text element."* with its own scenario asserting `aria-describedby` on the trigger.
- Implementation (`src/components/ui/HelpTip.tsx:9-16,58-59`) explicitly and deliberately does the opposite, with its own documented rationale: *"NO usa `aria-describedby`: una descripción que aparece y desaparece se anuncia de forma inconsistente entre lectores de pantalla. `aria-expanded` + `aria-controls` es el patrón que funciona igual en touch, teclado y AT."* This matches `design.md` §E word-for-word, which explicitly rejected `aria-describedby` for the same reason.
- This is a genuine spec-vs-design disagreement that was never surfaced or resolved during `sdd-design`/`sdd-tasks` — the design silently overrode the spec instead of updating it. The design's technical argument is defensible (a toggled description is genuinely awkward via `aria-describedby` in some screen readers), but as written, `HelpTip.test.tsx` (which only tests `aria-expanded`/`aria-controls`) cannot and does not prove the literal spec requirement, because the implementation doesn't do what the spec says. This should go back through spec update, not silently ship as-is.

**4. `closed_at` is not populated on every status-transition-to-`closed` path — one pre-existing, untouched path still leaves it NULL.**

- `db/migrations/200_functions.sql:1224` (`confirm_resolution`, rejected-dispute branch, not re-declared by this change) sets `update public.predictions set status = 'closed' where id = ...` with no `closed_at`. Every closing path this change actually touched (`finalize_predictions` steps 3 & 4, `request_close`) does set it correctly — grepped and confirmed.
- Practical impact is low: `score_prediction` is only invoked from the *successful*-resolution branch of `confirm_resolution` (which does set `resolved_at`, a valid `coalesce()` fallback), not from the rejected-dispute branch, so the NULL-earliness bug is not reintroduced through this gap. The observable symptom is cosmetic: `PredictionDetail.tsx:241-251` falls through to "cierra cuando lo pida el grupo" for a prediction that is actually already `closed` (via a rejected dispute) with `closes_at = NULL`, until/unless it's later resolved.
- This function was out of the assigned task list (`tasks.md` only lists `refresh_prediction_counts`, `finalize_predictions`, `create_prediction`, `cast_vote`, `add_prediction_option`, `score_prediction`, `notify_change` for re-declaration), so this isn't a deviation from `tasks.md` — but it does mean the orchestrator's "every path that closes a prediction" instruction is not fully satisfied by the current diff.

### SUGGESTION

**5. `README.md` still describes the old fixed-3 model** (`~line 21`: "si en 48 horas no la eligen al menos 3 personas"; `~line 478`: "`minimum_participants` a un mínimo de 3") and a stale "todo lleva noindex" line. Already self-disclosed in `apply-progress.md`'s Deviations §4 as out of scope/documentation-only — flagging here only for completeness, not as new information.

**6. `required_close_requests`'s floor of 2 can exceed a 1-member group's member count** (`greatest(2, least(member_count, ...))` → 2 when `member_count = 1`), unlike `required_participants`, which is provably always `<= member_count`. This is baked into `design.md` itself (not an apply-time deviation), and is a narrow edge case (a functioning group needs >1 member for predictions to be meaningful at all), but it means an open-ended prediction in a 1-member group can never close via quorum. Worth a one-line note in a follow-up, not a blocker.
